# DVC First Stage Plan

This document proposes the first conceptual stage for DVC-light implementation and outlines the readiness gate for actual DVC initialization.

## Purpose

The purpose of this document is to define the first executable DVC stage candidate, outline its command and dependencies, clarify the pending decisions required before DVC can be initialized, and provide a concrete readiness checklist for the future initialization task.

## Current Status

**DVC is not currently initialized.** This document is purely for planning purposes. No data movement has occurred, and no `dvc init` or `dvc add` commands have been executed. The formal target generated-output path remains pending.

## Relationship to DVC-light Policy

This plan strictly adheres to the repository's DVC-light policy:
*   DVC will be used for `dvc.yaml`, `dvc.lock`, stage metadata, dependency declarations, and reproducibility checks.
*   Source data and retained artifacts remain Git-primary.
*   A DVC remote is not required for ordinary repository use.
*   `dvc add` must not be run on raw/source data or retained artifacts.

## Relationship to `dvc_tracking_plan.md`

This document (`dvc_first_stage_plan.md`) proposes the first *executable DVC-light stage*.
The existing `dvc_tracking_plan.md` document lists *Git-primary dependency candidates* (such as `gpx/raw/` and `processed/えひめの山.xlsx`).
The two documents are complementary: `dvc_tracking_plan.md` identifies the inputs, while this document identifies the first process that will consume those inputs under DVC management.

## Conceptual Candidate: `detect_summit_candidates_preview`

The suggested first DVC-light stage candidate is a preview of the summit candidate detection process using the portable `detect-candidates` agent skill.

### Why this candidate?

This process relies purely on immutable GPX parsing and does not require complex YAMAP metadata joining or legacy mountain name assignment logic. It produces a straightforward CSV output, making it an ideal first test of DVC-light dependency tracking and reproducibility checks without risking data migration interference.

### Proposed Execution Command

```sh
node .agents/skills/yama-data-pipeline/cli.js detect-candidates --input gpx/raw --out <generated-output-path>/summit_candidates.csv
```

*Note: `<generated-output-path>/summit_candidates.csv` is a conceptual placeholder. The formal output path decision is pending.*

### Candidate Dependencies (`deps`)

*   `.agents/skills/yama-data-pipeline/` (the execution logic)
*   `gpx/raw/` (the immutable source data)

### Candidate Output-Path Decision

*   The output will be the CSV generated by the command.
*   Currently, `docs/migration/summit_candidates_skill_preview.csv` exists as an acceptable small committed preview/audit artifact.
*   **Crucially:** `docs/migration/summit_candidates_skill_preview.csv` should not automatically become the canonical DVC stage output. The `docs/migration/` directory is reserved for canonical planning, audits, and documentation, and is not ideal as a long-term generated-output directory.
*   A future generated-output path outside `docs/migration/` must be selected during the actual DVC initialization task.
*   The physical `data/` layout is still not to be implemented yet.
*   Therefore, the path remains conceptually `<generated-output-path>/summit_candidates.csv` until that explicit decision is made.

### Output Tracking Policy Options

Once the formal output path is decided, its tracking mode must be chosen:
*   **Git-tracked:** Committed directly to the repository (if small/text-based).
*   **DVC-tracked:** Managed by DVC and ignored by Git (if large/binary or if a remote is eventually introduced).
*   **Both:** DVC tracks metadata, Git tracks content (rarely recommended unless highly specific).
*   **Regenerated-on-demand:** Neither tracked by Git nor DVC cache, but simply ignored by Git and rebuilt by the pipeline when needed.

## Recommended Next Decision

Before DVC initialization can proceed, a formal decision must be made regarding the concrete path for `<generated-output-path>/summit_candidates.csv` that avoids both `docs/migration/` and a premature `data/` directory rollout.

## DVC Initialization Gate Checklist

The future task that actually initializes DVC must verify the following before execution:

- [ ] DVC is installed in the execution environment.
- [ ] No protected data movement is proposed or executed.
- [ ] No `dvc add` is run on raw/source or retained artifacts.
- [ ] `dvc init` is run *only* after explicit task approval.
- [ ] A generated output path has been selected and documented.
- [ ] An output tracking mode (Git-tracked, DVC-tracked, regenerated-on-demand) has been selected.
- [ ] The `dvc.yaml` stage command is reviewed and correct.
- [ ] The dependency list is reviewed and accurate.
- [ ] Protected data paths are checked after execution to ensure no unintended modifications.
- [ ] No DVC remote is required for ordinary use.
- [ ] A clear validation command is recorded to verify stage reproducibility.

## Explicit Non-Goals

The following remain explicitly prohibited during the current planning phase (and until specifically authorized in a future task):
*   Running `dvc init`, `dvc add`, `dvc repro`, `dvc push`, or `dvc pull`.
*   Creating `.dvc/`, `.dvcignore`, `dvc.yaml`, or `dvc.lock`.
*   Running `git lfs install` or `git lfs track`.
*   Implementing Kedro pipelines (`kedro new`).
*   Modifying, moving, renaming, deleting, normalizing, or format-converting any protected data in `gpx/`, `csv/`, `processed/`, `yamap/`, `reverse_geocoding/`, or `museum-yama-web/`.

## Validation Expectations for a Future DVC Task

A future task implementing this plan must be able to demonstrate that:
1. `dvc repro detect_summit_candidates_preview` successfully rebuilds the output if dependencies change.
2. `git status` shows no unintended modifications to raw/source data.
3. The pipeline output matches expected validation metrics (e.g., CSV row counts vs source track counts).
